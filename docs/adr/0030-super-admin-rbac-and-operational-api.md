# ADR-0030: SUPER_ADMIN RBAC and operational API

## Decision

`USER`, `ADMIN`, and `SUPER_ADMIN` are additive account roles resolved from the server-side access session. `AUTH_ADMIN_GOOGLE_SUBS` is an initial four-account trusted cohort: each matching Google identity is promoted to `ADMIN` on login, never directly to `SUPER_ADMIN`. An active `ADMIN` can bootstrap exactly one first `SUPER_ADMIN`; a transaction-scoped PostgreSQL advisory lock serializes the absence check and historical-bootstrap check.

To establish the second permanent `SUPER_ADMIN` without allowing the first one to manufacture an approver, an `ADMIN` target must present an independently issued external approval JWS to `POST /api/v1/admin/super-admin/break-glass`. The token is bound to the target account, environment, audience, action, and an expiry of at most 24 hours. Its `jti` hash is consumed durably in PostgreSQL, so replay fails across restart, scale-out, and deployment. The API never receives or stores the signing private key; it verifies with the configured public key.

After the temporary second `SUPER_ADMIN` is active, a third cohort member creates the request to promote the intended second permanent administrator; the original and temporary `SUPER_ADMIN` accounts approve independently. The temporary account expires back to `ADMIN` after its bounded TTL. Later role changes are durable requests with two distinct currently active `SUPER_ADMIN` approvers. Requester and target cannot approve or be the same account; self-demotion and removal of the final active super administrator are refused. Bootstrap, role changes, break-glass elevation, expiry, and recovery revoke affected sessions server-side.

## Consequences

The HTTP API exposes the read-only operational snapshot, protected bootstrap/break-glass/request/approval flows, and pending-request reads through the BFF mTLS boundary. Break-glass requires an active target `ADMIN` session and an independently signed external approval; there is no endpoint that lets the sole `SUPER_ADMIN` mint its own second approver. `LOCKOUT_RECOVERY` (zero active `SUPER_ADMIN` accounts after historical bootstrap) remains an infrastructure change-ticket/runbook flow and is not exposed as an application mutation endpoint. The snapshot is an exact allowlist from the AI read-model seam: `health: healthy`, `readiness: ready`, aggregate processing-job status, failure-code classes, and `resources: [processingJobs]`. `healthy` and `ready` are emitted only after both aggregate reads of `ai.processing_jobs` succeed; the API does not infer them from `SELECT 1`. It intentionally excludes source text, prompts, raw provider errors, secrets, tokens, PII, and billing values.

With exactly two active `SUPER_ADMIN` accounts, a role-change request targeting either one is intentionally unavailable: the target and requester are excluded, leaving fewer than the required two independent approvers. Operators must first expand the quorum through the approved temporary break-glass flow; this safety invariant prevents a single remaining approver from unilaterally demoting or replacing the other account.

`GET /api/v1/admin/super-admin/bootstrap/status` is restricted to active `ADMIN`/`SUPER_ADMIN` sessions and returns only the mode (`FIRST_BOOTSTRAP`, `SEED_SECOND`, `QUORUM_RECOVERY`, `NORMAL`, `LOCKOUT_RECOVERY`, or `UNAVAILABLE`). The active count remains an internal repository value used to derive that mode and is not part of the public response. The mode is derived from current quorum and immutable audit history; a previous bootstrap does not permanently hide recovery when the quorum later falls to one.

`POST /api/v1/admin/super-admin/break-glass` accepts only `{ approvalToken }`. The token must be a compact JWS with `RS256`, exact configured issuer/audience/environment, action `GRANT_BREAK_GLASS_SUPER_ADMIN`, target UUID equal to the current session, and a bounded future `exp`. No raw token or private key is logged.

`GET /api/v1/admin/super-admin/role-change-requests?status=pending&limit=50` returns at most 50 unfinished, unexpired role-change requests, ordered by `createdAt DESC, id DESC`; each request expires after 30 minutes. `SUPER_ADMIN` can see all pending requests; `ADMIN` can see only requests that they created. Each item is limited to `id`, `requesterId`, `targetUserId`, `desiredRole`, `createdAt`, `approvalCount`, `requiredApprovals: 2`, and `canApprove`. `approvalCount` includes only approvals from active, eligible `SUPER_ADMIN` accounts. `canApprove` is true only for an active `SUPER_ADMIN` who is neither the requester nor the target. The endpoint does not expose email addresses, names, credentials, tokens, source data, or other PII; `nextCursor` is currently `null` because the bounded response does not yet implement cursor pagination.
